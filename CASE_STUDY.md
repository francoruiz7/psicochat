# PsicoChat — Case Study

A conversational web app that uses an LLM (via the OpenAI API) as a
therapeutic support space, with persistent memory across sessions, risk
detection, and streamed responses.

## The core design problem

The tension that shaped most of the technical decisions was this: **the
interface had to feel like discrete sessions** (the person comes in,
talks, leaves, and the next time starts fresh — they don't want to reopen
an endless chat stuck on the last sentence from three weeks ago), **but
the system needed real memory** of everything discussed before, to
provide genuine continuity instead of "amnesia" between visits.

The solution was to separate two layers that are often treated as one:

- **Session** = the interface unit (a fresh greeting, an explicit close)
- **Evolving profile** = a cumulative summary that persists in the
  background, regenerated by an auxiliary model when each session closes,
  and injected into the following session's system prompt

This avoids two problems at once: no need to drag along the full
conversation history (expensive, and eventually exceeds the model's
context window), and the person doesn't have to "re-explain everything"
to the system every time they come back.

## Identity without a full account system

The project is for personal use, so a complete authentication system
(email, password recovery, verification) would have been over-engineering.
It was solved with a simple username + password (hashed with
PBKDF2-HMAC-SHA256 and a salt, never in plain text), enough for memory to
work across devices without depending on one browser's `localStorage`.
Explicitly documented as insufficient if the project were ever opened up
to more than one person.

## Security as independent layers, not a single prompt

Instead of putting all the safety responsibility on the main
conversational model (whose system prompt is long and nuanced, optimized
for psychological depth, not for safety), risk detection runs as a
**separate, deterministic classification** on each message, using a
simpler model. If risk is detected, the UI shows a fixed banner with help
resources — it doesn't depend on the main model "remembering" to mention
it well in its free-text reply. The two layers are independent: if one
fails (e.g. the classifier has a technical error), the other still stands.

## Cost kept under control without sacrificing quality

With a system prompt of about 700 lines, the cost of sending it on every
call could have been a real problem. Two decisions solve it:

1. The static block of the prompt always goes first and identical on
   every call, to take advantage of OpenAI's prompt caching (a strong
   discount on that repeated portion). The profile summary is always
   appended after it, never mixed in, so it doesn't invalidate that
   caching.
2. Auxiliary tasks (session summary, risk classification) use a cheaper
   model than the main conversational one — they don't need the same
   depth.

## Streaming as a product decision, not just a technical one

In a space meant to hold an emotionally sensitive conversation, waiting
in silence for a full block of text to appear feels different from
watching the reply build in real time. Streaming was implemented via
Server-Sent Events, with a non-streaming alternative endpoint (`/chat`)
for simple debugging.

## Known limitations (intentional, not oversights)

- No password recovery — if it's forgotten, access to that profile is
  lost (acceptable for a single user).
- Geolocated help resources are a simple keyword mapping over free text,
  not real geolocation.
- SQLite in a single file — adequate for personal use, not built to scale
  to multiple concurrent users.
- The cost model assumes the project owner pays for their own API key;
  it isn't designed to open up to other users without adding billing or
  a bring-your-own-key (BYOK) scheme.
